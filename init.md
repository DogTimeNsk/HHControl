# Задача: разработать MVP проекта HH Control

Ты — Senior Fullstack Engineer с опытом Python, FastAPI, Vue 3, Docker и интеграций со сторонними REST API.

Необходимо разработать небольшое self-hosted веб-приложение для управления публикацией собственных резюме на hh.ru через официальный API HeadHunter.

Проект должен быть простым в установке, надёжным и расширяемым для дальнейшего развития.

## 1. Назначение

Пользователь подключает свой аккаунт hh.ru, получает список резюме и выбирает, какие из них необходимо автоматически обновлять.

Приложение каждые 4 часа проверяет выбранные резюме и, если API HeadHunter разрешает повторную публикацию, выполняет обновление.

Пользователь может включать и выключать автоматическое обновление для каждого резюме отдельно.

В дальнейшем приложение будет расширяться аналитикой и другими функциями, поэтому архитектура не должна быть жёстко привязана исключительно к публикации резюме.

## 3. Интеграция с HeadHunter API

Базовый URL:

https://api.hh.ru

Использовать официальный публичный API там, где метод доступен. Для операций
с собственными резюме соискателя допускается browser automation через
Playwright, поскольку поддержка applicant API прекращена 15 декабря 2025.

Перед реализацией проверить актуальную спецификацию:

https://api.hh.ru/openapi/redoc

Методы, которые необходимо изучить:

- GET /resumes — получение резюме пользователя.
- GET /resumes/{resume_id} — получение деталей.
- POST /resumes/{resume_id}/publish — публикация или обновление даты резюме.

Проверить доступность методов, требования к OAuth scopes и ограничения API.

Не придумывать поля и методы официального API. Browser automation должна
работать только через обычный интерфейс hh.ru, доступный пользователю.

### Авторизация

Использовать OAuth2 для доступных официальных методов. Для browser automation
использовать отдельную браузерную сессию соискателя: пользователь проходит
вход вручную в управляемом браузере, после чего приложение безопасно хранит
состояние сессии локально.

Предусмотреть:
- Client ID и Client Secret через переменные окружения.
- OAuth Authorization Code Flow.
- Безопасное хранение пользовательских токенов.
- Обновление access token через refresh token, если поддерживается.
- Обработку истечения срока действия авторизации.
- Повторное подключение аккаунта при необходимости.

Если пользователь предоставляет готовый OAuth access token, предусмотреть возможность его настройки через защищённую конфигурацию для первоначального запуска.

Не считать обычный API-ключ эквивалентом пользовательского OAuth access token.

Не выводить токены в логи и не передавать их frontend после подключения.

Не хранить пароль hh.ru. Не обходить CAPTCHA, MFA, ограничения частоты
действий, антибот-защиту или другие механизмы контроля сайта.

Использовать требуемые HH-User-Agent / User-Agent заголовки.

## 4. Управление резюме

Backend должен получать список собственных резюме пользователя через HH API,
если метод доступен, либо через browser automation в личном кабинете hh.ru.

Каждое резюме отображается в dashboard и содержит:

- Название.
- ID резюме.
- Текущий статус.
- Дату последнего обновления.
- Следующую разрешённую дату публикации (если API возвращает).
- Включено ли автоматическое обновление.
- Результат последней попытки.
- Время следующей проверки.

Предусмотреть:
- Синхронизацию списка резюме с HH.
- Добавление новых резюме через синхронизацию.
- Отключение резюме от автоматического обновления.
- Удаление резюме из локального списка управления без удаления его на hh.ru.
- Ручной запуск обновления отдельного резюме.

После синхронизации новые резюме должны быть выключены по умолчанию.

## 5. Планировщик

Использовать APScheduler.

Проверка должна происходить каждые 4 часа.

Интервал конфигурируется через ENV:

SCHEDULER_INTERVAL_HOURS=4

Алгоритм:

1. Получить из локальной БД список резюме с включённым автоматическим обновлением.
2. Для каждого резюме проверить состояние в HH API либо в личном кабинете.
3. Проверить, разрешена ли публикация в личном кабинете.
4. Если есть next_publish_at, учитывать серверное время с корректным timezone.
5. Если обновление ещё недоступно — пропустить резюме без попытки публикации.
6. Если публикация разрешена — выполнить штатное действие обновления в
   интерфейсе hh.ru через Playwright.
7. При успешном ответе обновить локальные данные.
8. Записать результат выполнения в историю.
9. Продолжить обработку остальных резюме, даже если одно завершилось ошибкой.

Периодическая проверка не должна принудительно обновлять резюме вопреки ограничениям HeadHunter.

Предусмотреть:
- Защиту от параллельных запусков одной задачи.
- Таймауты HTTP-запросов.
- Ограниченные retry для временных сетевых ошибок.
- Уважение Retry-After и 429.
- Отсутствие повторной публикации после неопределённого результата HTTP-запроса без проверки состояния.
- Запрет на бесконечные retry.
- Пропуск недоступных или заблокированных резюме.
- Логирование каждой попытки.
- При появлении CAPTCHA, MFA или другого интерактивного препятствия остановить
  задачу и запросить ручное действие пользователя; не пытаться обходить его.

Планировщик должен работать отдельным процессом или сервисом Docker Compose, независимо от количества backend workers.

## 9. Безопасность

Приложение предназначено для личного использования.

Но необходимо предусмотреть базовую защиту:

- Авторизацию доступа к dashboard.
- Безопасное хранение секретов.
- Отсутствие токенов в логах и frontend.
- Защиту API от неавторизованных вызовов.
- Защиту OAuth callback от CSRF через state.
- Корректную работу за reverse proxy.
- Не публиковать SQLite и внутренние endpoints наружу.
- Не хранить реальные credentials в Git.

Для MVP допустима простая локальная авторизация через пароль администратора с защищённой сессией.

Не использовать открытый dashboard без авторизации.

## 10. Docker

Создать:

- Dockerfile.backend
- Dockerfile.frontend
- docker-compose.yml
- .env.example
- .dockerignore

Разделить процессы:

- api — FastAPI backend.
- scheduler — APScheduler worker.
- frontend — Nginx со статической сборкой Vue.

Backend и scheduler используют общий persistent volume SQLite.

Обеспечить корректную работу SQLite при доступе из двух процессов, использовать WAL и busy_timeout, но не рассчитывать на SQLite как на распределённую очередь.

Добавить healthcheck и политику перезапуска.

Запуск одной командой:

docker compose up -d --build

## 13. Что НЕ нужно делать в MVP

Не реализовывать:

- Массовые отклики на вакансии.
- Парсинг вакансий.
- Аналитику работодателей.
- AI-анализ резюме.
- Telegram-бота.
- Мультипользовательский SaaS.
- Kubernetes.
- Сложную систему ролей.
- Изменение содержания резюме.

Не использовать неофициальные мобильные API. Playwright разрешён исключительно
для взаимодействия с собственным личным кабинетом пользователя через обычный
веб-интерфейс. Нельзя обходить CAPTCHA, MFA, лимиты, защитные механизмы или
скрывать факт автоматизации.

- Асинхронные HTTP-запросы.
- Type hints для Python.
- Pydantic для валидации.
- Разделение бизнес-логики и HTTP-слоя.
- Безопасное управление токенами.
- Отсутствие захардкоженных секретов.
- Понятные логи.
- Минимум лишних зависимостей.
- Расширяемая архитектура без избыточных абстракций.
- KISS / YAGNI.

2. Сформировать минимальную архитектуру проекта.
3. Реализовать backend и интеграцию, включая Playwright browser worker для

5. Реализовать dashboard.
6. Настроить Docker Compose.
7. Написать тесты.
8. Подготовить README с инструкциями запуска и настройки OAuth.
9. Проверить сборку и запуск приложения.

В README отдельно описать, какие полномочия, токены и browser session нужны
для работы с резюме, а также возможные ограничения повторной публикации и
риски browser automation.

credentials и с реальной browser session.
